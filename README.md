# Fashion Fiesta Hub

Storefront and admin dashboard for a ladies fashion brand in Nairobi, Kenya.

This is a **schema-first rebuild**. The previous workspace was a Vite + React app where the
storefront and the admin dashboard each carried their own hardcoded fixtures — the two agreed
only because they were kept in sync by hand, and every admin edit was `useState`-only, so they
diverged on first mutation. That is a data-model problem, not a component problem, so the
database comes before any UI.

## Stack

| | |
|---|---|
| Framework | Next.js 15 (App Router) |
| Language | TypeScript, `strict` |
| Styling | Tailwind v4 (`@theme` in `src/app/globals.css`) |
| Database | Supabase — Postgres + RLS |
| Local dev | Docker + Supabase CLI |
| Deploys | Vercel, from `main` |

## Getting started

```bash
npm install
cp .env.example .env.local
npm run dev
```

App runs at http://localhost:3000.

### Local database

```bash
supabase start
supabase db reset   # applies every migration, then seeds
```

`supabase db reset` is the definition of done for the schema phase: it must rebuild a seeded
local database from scratch with no manual steps.

## The three rules

These are structural, not conventions. Each one fixes a specific bug found in the old app.

### 1. Order history is immutable

`order_items` stores `title_snapshot`, `sku_snapshot`, `size_snapshot`, `color_snapshot`,
`unit_price_kes`, `qty` and `line_total_kes` as they were **at time of purchase**. Nothing in
the order path reads live product data. Admin edits a product title or price and every past
order still reads correctly — that is what makes the two halves of the app agree.

`order_items.variant_id` is `ON DELETE SET NULL`, never `CASCADE`. Deleting a variant must not
delete the order lines that reference it.

### 2. Order numbers are unguessable by construction

`orders` has two identities: `id bigserial` (internal, never exposed) and `order_number text`
(public). The public one is `FFH-` plus 10 Crockford base32 characters — `0-9A-Z` minus
`I`, `L`, `O`, `U` — for roughly 2^50 possibilities. It is **random, not a sequence**, so it
leaks neither order volume nor ordering. Generated by a `set_order_number()` trigger using
`gen_random_bytes`, retrying on unique violation.

This matters because phone + order number *is* the credential for order lookup, and Kenyan
mobile numbers are enumerable. The order number carries all the entropy. `FFH-001` is retired
permanently.

### 3. Money is computed server-side, once

Subtotal, delivery fee and total are computed in one server-side transaction at order creation,
from variant prices read under `FOR UPDATE`. The client sends variant ids and quantities —
**never prices, never totals**, so nothing on the browser can influence what is charged.

All money is `integer` whole KSh. M-Pesa transacts in whole shillings; floats here would be a
defect.

## Access control

Row Level Security is on from day one, not retrofitted:

- `products` — readable where `status = 'active'`
- `orders` / `order_items` — readable only by their owner
- staff access via a `staff` table, checked in middleware

Customer PII never ships to the browser. Guest checkout: identity is phone + order number,
verified server-side.

## Environment

`.env.example` documents every variable. `SUPABASE_SERVICE_ROLE_KEY` is server-only and must
never be prefixed with `NEXT_PUBLIC_` — that would bypass RLS entirely.

`NEXT_PUBLIC_SITE_URL` is the canonical production origin used for `metadataBase`, robots and
sitemap. Set it to the real domain before deploying.
